# Решения и допущения

## Где ТЗ не даёт однозначного ответа

1. **Удаление и неудаляемая история.** ТЗ разрешает постановщику удалять задачи и запрещает удалять историю. Настоящее удаление снесло бы и её, поэтому удаление мягкое: задача получает пометку и исчезает для всех, а история остаётся в базе. Прямой `DELETE` закрыт даже постановщику.
2. **Удаление объекта с задачами.** Объект удаляется вместе со своими задачами, тоже мягко. Перед этим интерфейс показывает, сколько задач затронет. Запрещать удаление, пока есть задачи, не стал: ТЗ даёт постановщику удалять объекты без условий.
3. **Исполнитель обязателен при создании задачи.** Задачу без исполнителя некому брать в работу, такого состояния в таблице переходов нет.
4. **Смена исполнителя возможна в любом статусе.** Статус при этом сохраняется, новый исполнитель продолжает с него, прежний сразу теряет доступ к задаче и её истории.
5. **Принять или вернуть может любой постановщик,** не только автор задачи: в ТЗ сказано «постановщик», и их может быть несколько.
6. **Постановщик не двигает задачу за исполнителя.** По таблице ТЗ брать в работу и отправлять на проверку может только назначенный исполнитель. Если он недоступен, постановщик назначает другого.
7. **«Принята» считается конечным статусом,** выхода из него в таблице нет. Поля принятой задачи постановщик править может: ТЗ не запрещает, а история статусов от этого не меняется.
8. **Комментарий к остальным переходам необязателен,** но сохраняется, если написан. Строка из пробелов и переводов строки комментарием не считается.
9. **У пользователя одна роль.** Назначить можно только исполнителя, это проверяет база. Новый пользователь Supabase получает роль исполнителя автоматически, постановщика назначают вручную в таблице `profiles`: так ошибка при заведении не даёт лишних прав.
10. **Карточка объекта у исполнителя показывает только его задачи.** ТЗ просит список задач объекта, но запрещает читать чужие. Безопасность важнее.
11. **Кого видит исполнитель из людей:** себя, авторов своих задач и тех, кто есть в их истории. Общего списка сотрудников нет, адреса почты хранятся только в Supabase Auth и через таблицы приложения не читаются.
12. **Чужая и несуществующая задача дают один ответ:** «Задача не найдена». Так нельзя выяснить, существует ли задача с таким id.
13. **Экран «Все задачи» для постановщика сверх ТЗ.** Это тот же экран, что «Мои задачи», с фильтром по статусу. Без него задачи на проверке пришлось бы искать по объектам.

## Как это устроено и почему

- **Смена статуса идёт через одну функцию,** `change_task_status`. Колонка `status` закрыта для прямой записи всем, включая постановщика. Функция блокирует строку, сверяет переход с таблицей `task_transitions`, проверяет роль и комментарий, меняет статус и пишет историю в одной транзакции. Блокировка нужна для двух одновременных решений: второе увидит уже новый статус и получит отказ.
- **Кнопки приходят из базы.** Функция `available_transitions` читает ту же таблицу переходов, поэтому правила не дублируются на фронтенде.
- **Два слоя прав.** `GRANT` на колонки решает, что можно писать в принципе (автора, статус и даты нельзя никому), RLS решает, какие строки доступны конкретному пользователю. Всё новое в `public` закрыто по умолчанию.
- **Роль лежит в таблице `profiles`, а не в `user_metadata`:** метаданные пользователь может менять сам через API. Смена роли срабатывает сразу, без перевыпуска токена.
- **История защищена дважды:** записи через API нет ни у кого, а триггер запрещает изменение и удаление даже администратору базы и `service_role`.
- **Служебные функции в схеме `private`,** она не опубликована в API.
- **Публичный ключ демо-стенда лежит в `.env.example`.** Он и так виден в браузере любого посетителя, защиту держит база. Секретного ключа нет ни в коде, ни в сборке, ни в настройках Vercel. Пароли демо-стенда в репозитории нет, в `supabase/seed.sql` только пароль для локального запуска.
- **Советник безопасности Supabase показывает 4 предупреждения, все разобраны.** Три про `SECURITY DEFINER` у `change_task_status`, `delete_task` и `delete_object`: это сознательно, функции меняют закрытые колонки, а вызывающего определяют сами через `auth.uid()`. Четвёртое про проверку паролей по базе утечек: доступна только на платном тарифе.

## Что не успел или не стал делать

- Видео не записывал, объяснение для руководителя текстом: [for-manager.md](./for-manager.md).
- В интерфейсе нет корзины: удалённое восстанавливается только запросом в базу. Кто именно удалил, не записывается.
- Смена исполнителя и правки полей задачи не попадают в историю, ТЗ просит только смену статуса.
- Нет уведомлений, поиска, постраничного вывода и вложений.
- Нет смены и сброса пароля в интерфейсе, пользователей ведёт администратор в Supabase.
- Демо на бесплатном тарифе Supabase: проект засыпает после недели без обращений и просыпается вручную из панели.
